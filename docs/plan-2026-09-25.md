# Improvement plan, 25 September 2026

Findings from a review of the code, the 151-run evidence set, and 136 live
routing decisions. Ordered by how much each item changes what the router does.

## Where things stand

The router runs in every pi session but has never switched a model outside
tests. 136 decisions are recorded; all but 17 are shadow mode. Of five
classifier questions, one influences the pick. The evidence base is sound for
code and writing and thin for planning. The frontier selector had a sign fault
until yesterday that chose the worst value on a concave frontier.

## 1. The context block reads the wrong side of the transcript

**Finding.** Since the context fix, 34 of 39 live classifications still came
back `unclear`. The collector works: replaying a real session file through it
yields three prior turns and the tool list. The prior turns were "make sure to
fix all and continue with the paper", "continue", and "investigate and /plan
further improvements". In an agentic session the user's turns are mostly
continuations. The work is described by the assistant's last message and the
tools it called, which the collector does not read.

The same session's last assistant text was "Fixing `\times` became a tab in
manuscript.tex". That is a mechanical LaTeX edit. "continue" means that.

**Change.** Add to `readSessionSignals`:

- the last non-empty assistant text, clipped to 240 characters
- the distinct file paths from the last 20 tool calls, most recent first
- the last two bash commands, clipped

Put these in the context block under "Work in progress". Keep the user-turn
line; it still helps when the user does state the task.

**Test.** Replay the recorded session that produced `unclear` for "continue"
and assert the category is no longer `unclear`. Then watch the live ledger:
the target is under 20% `unclear` on continuation prompts, down from 87%.

**Cost.** One module, one test. No new API calls; the assistant text is
already in the session.

## 2. Four of five classifier answers are unused

**Finding.** `selectModel` reads `category` (through `workKind`) and gates on
`risk >= 2`. `complexity` is computed and returned but never read.
`brief` and `decompose` do not appear in the selector. The router pays for
five answers and acts on one and a half.

**Change, in order of confidence.**

*Complexity → cost aversion.* `PROFILE_WEIGHTS.lambda` is fixed per kind.
Scale it by complexity so a hard task tolerates more cost: at complexity 0
use 1.5× lambda, at 3 use 0.5×. This is the only use that changes the pick
directly and it is cheap to test against the ledger.

*Brief → abstain.* When `brief` is `clarify` with confidence above 0.7, the
router should not switch models at all. The task is not defined well enough
to route. Record the decision with reason `brief_unclear` and leave the
current model in place.

*Decompose → dispatch hint.* When `decompose` is above 0.7 on a code task,
add a line to the system prompt suggesting `dispatch_task`. Do not dispatch
automatically; that is a behaviour change the user did not opt into.

*Risk.* Already gates the proven-runs check. Leave it.

**Test.** Fixture-level for each rule. Then replay the 136 recorded
classifications through the new selector and diff the picks, so the effect
is visible before anything goes live.

## 3. Planning evidence is one run per cheap model

**Finding.** Planning routes to `glm-5.3-flash` on 1 of 1. Sonnet has 4 of 4.
The original suite had one planning task and nothing since has added another.
The planning verifier checks for the presence of five keywords, which every
model clears; it separates nothing.

**Change.** Two planning tasks with a verifier that can fail:

- *Migration plan with a hard constraint.* The prompt gives a schema change
  that must be backwards compatible for one release. The verifier checks
  for an explicit expand-and-contract sequence and rejects a plan that drops
  a column in the same release it stops writing to it.
- *Incident runbook decomposition.* The prompt gives a multi-system failure
  and asks for ordered steps with owners. The verifier checks that no step
  depends on a later step and that every named system has an owner.

Both verifiers get the red/green control the code tasks had: fail on a
bare starting state, pass on a hand-written correct plan, fail on a plausible
wrong plan.

**Cost.** About $0.40 for four models × two tasks × two passes, almost all
Sonnet.

## 4. A timeout is scored as a wrong answer

**Finding.** Five of deepseek's seven code failures in the last run were the
180-second wall-clock cap, not the verifier. Its mean code latency is 90s
against 22s for the others. The cap is currently part of correctness.

That is defensible as a routing signal, since a user waits for the answer,
but it conflates two things the frontier already separates. Latency has its
own axis and its own weight (`mu`).

**Change.** Record `timedOut: true` on the run and score it at read time,
like the turn budget. `scoreRow` treats a timeout as a failure by default
but exposes `TIMEOUT_IS_FAILURE` so the two views can be compared. Keep the
default: a model that does not finish did not solve the task.

**Test.** The evidence test asserts both views on a fixture with one timeout.

## 5. The knee depends on which extreme models exist

**Finding.** The knee is the point farthest above the chord between the
frontier's endpoints. Removing a $0 stealth model moved the code pick from
`ling` to `glm`. Both were defensible, but the route changed because
OpenRouter listed a preview that week. Yesterday's sign fix means the knee
now returns nothing on a concave frontier and falls through to tangency,
which reduces the exposure, but the chord is still anchored on whatever is
cheapest and best that day.

**Change.** Anchor the chord on measured models when any exist. If the
frontier contains at least two models with evidence for this kind, draw the
chord between the cheapest measured and the best measured, and only consider
points above that chord. Unmeasured models can still win if they sit above
it. If fewer than two are measured, use the current full-frontier chord.

**Test.** A fixture with one measured pair and one unmeasured extreme on each
side: adding or removing the extremes must not change the pick.

## 6. Nothing has ever been switched live

**Finding.** Shadow mode is the default and has stayed on. That was the right
call while the classifier returned `unclear` on most prompts and the knee had
a sign fault. After items 1 and 2 land, the remaining risk is a bad pick on a
task the user cares about, which the user can undo with `/router pin`.

**Change.** Do not flip the default. Instead, add `/router auto --dry-run N`:
switch models for the next N tasks, then return to shadow and print a
summary of what was chosen, at what cost, with what verifier outcome where
one exists. That gives a bounded trial without a standing commitment.

## 7. Smaller items

- **Ledger does not store the context block.** Store the first 400
  characters. Diagnosing item 1 required replaying a session file by hand.
- **Board has two tasks stuck in `verifying` since 20 September.** Add a lease
  timeout: a task in `verifying` for more than 24 hours moves to `blocked`
  with a reason, and `/chief board` shows it.
- **`gpt-5.4-mini` has n=2 on writing.** It was the original writing route
  and is now beaten by `deepseek` on 12 of 12. Either add it to the model set
  for the next writing pass or drop it from the docs.
- **Subscription routing has never been exercised.** Every Codex model was
  either unsupported or at its limit when probed. Re-probe after the limit
  resets and record the outcome before recommending it.

## What this plan does not do

It does not add models to the benchmark set. Four models across three price
tiers is enough to shape the frontier; the gap is in task coverage and in
which signals reach the selector, not in model coverage.

It does not change the turn budget or the quality floor. Both were placed by
looking at gaps in the measured distribution, and neither has caused a wrong
pick since.

It does not propose a different selector. The frontier with a knee-then-
tangency fallback is working once the sign fault is out. The remaining
problems are inputs.

## Order

1, 2, 7 (ledger), 3, 5, 4, 6, then the rest of 7. Items 1 and 2 change the
most and cost the least. Item 3 needs API spend and should follow a working
classifier, or the planning evidence will be collected under `other`.
